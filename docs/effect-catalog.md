# サーバー登録効果カタログ

今後の開発基準は添付v3仕様です。[v3導入記録](effect-engine-v3.md)を先に参照してください。
この文書は既存kind形式DSLとローカル検証用機能の実装記録で、v3準拠や実カード裁定確認済みを意味しません。

EffectCatalogは、カード基本情報のマスターとは別に、サーバーが明示的に登録するDSL定義を保持します。
実カードの定義やファイルの自動読込は今回追加していません。既存CSV/card-master.jsonも変更しません。

## JSON形式

```json
{
  "catalogVersion": 1,
  "definitions": [
    {
      "dslVersion": 1,
      "effectId": "EXAMPLE.draw",
      "cardId": "EXAMPLE-LEADER",
      "trigger": { "kind": "activate", "window": "main" },
      "costs": [],
      "actions": [{ "kind": "draw", "player": "SELF", "amount": 1 }]
    }
  ]
}
```

これは架空の構造例です。実カードにこの効果があるという意味ではありません。
parseEffectCatalog(json)で形式番号とDSLを検証します。信頼するサーバーコードからは
new EffectCatalog(definitions)も使えます。パスの指定、実行コード、関数の登録は受け付けません。

## 検証と版固定

- effectIdはカタログ全体で一意です。同じIDを別カードへ登録しても拒否します。
- 各定義は既存DSL検証器を通し、入力から切り離したfreeze済みコピーを保存します。
- 上限は4096定義、全体8MiBです。定義ごとの65,536バイト等の既存制限も適用します。
- 版は検証後の定義をeffectId順に並べてハッシュ化します。入力順だけを変えても同じ版です。
- listForCard(cardId)はID・trigger・schemaOnlyの要約だけを返します。
- 登録・構造検証の成功は、そのカードが今その効果を実行できるという意味ではありません。
- card-masterのeffects/effectIds、表示用の手動効果は、実行定義へ自動昇格しません。
- カタログ本体をクライアントへシリアライズすることは禁止します。

## 盤面所有者からの発動

new EffectMatchOwner(match, catalog)で同じカタログを対戦中保持します。
openRegisteredEffect(effectId, actor, sourceRef, rules, numericPolicy?)で、現在のカード実体と
generationを確認し、そのcardIdに登録された定義だけを既存実行器へ渡します。
resolutionIdはサーバーがUUIDで生成します。クライアントから指定させません。

未登録ID、別カード、古い参照、別プレイヤーのカード、未対応の命令は開始前に拒否します。
発動タイミング・condition・コスト等の既存検証も引き続き必要です。
snapshotのcatalogVersionで使用版を識別できます。実行途中でカタログを差し替えるAPIはありません。

ローカルの固定テスト効果もこの登録経路へ変更しました。通常の公開起動は有効化していません。
登録済み効果一覧の参照通信は下記を参照してください。利用者が一覧から発動を選ぶUI、実カード定義、
ファイル配置・読込・マスターとの配布管理は今後の段階です。

## 一覧参照通信

`test-effect:catalog` は、自分の表向きのリーダー・キャラクター・ステージに
登録された効果の要約だけを、要求した接続へのackで返します。盤面は変更せず、相手へ配信しません。

要求は `matchId`、`expectedMovementRevision`、`expectedProgressionRevision`、
`source: { instanceId, generation }` です。プレイヤー番号はサーバーが接続から決めます。
古い盤面参照、相手カード、手札等の対象外エリア、不正な要求は拒否します。

成功時は `{ ok: true, catalog }` を返します。catalogには両revision、使用カタログ版、
カード参照、効果ID・trigger・`status: "schemaOnly"`・`timingAvailable` の一覧を含めます。
コストや処理定義の本体は返しません。カタログ未設定は版null・空一覧で明示します。

`timingAvailable` は起動効果のタイミングだけの判定です。コスト、回数制限などを含む
発動可能性の保証ではありません。イベント効果や処理待ち中はfalseです。
本番の自動効果は引き続き無効です。

## テスト画面での参照

自動効果のテスト盤面では、自分の表向きのリーダー・キャラクター・ステージを
タップすると、中央のダイアログにカード画像と登録済み効果一覧を表示します。
既存の中央パネルが盤面を覆う場合は「盤面を見る」でたたみ、
「効果処理に戻る」で復帰できます。処理段階が進むとパネルは自動で開きます。
たたむ前の未確定のカード選択も保持します。

サーバーで明示的に許可したローカルテストだけ、タイミングが一致する起動効果に
「発動する」を表示します。タイミング一致だけで発動可能と断定せず、サーバーで再検証します。
読込中、取得失敗、カタログ未設定、登録なしは区別します。
相手カードや手札はこれまでどおり詳細確認のみで、一覧要求を送りません。
盤面revision・処理段階・同期状態が変わった場合はダイアログを閉じます。
閉じた後の遅延応答、別試合、古いrevision/generationの応答は一覧へ反映しません。
通常オンライン対戦・一人回し・手動のテスト対戦の操作は変更しません。

## 一覧からの発動要求

`new EffectMatchOwner(match, catalog, true)` の明示指定が必要です。省略時は参照専用です。
`test-effect:command` に `kind: "activateRegistered"` を送信します。要求は通常の
matchId・現在のresolutionId・requestId・両revisionに加え、source参照、catalogVersion、effectIdです。
actor、処理定義、検証ルール等はクライアントから受け取りません。

自分の表向き盤面、登録カードと効果IDの対応、generation、カタログ版、両revision、
置き換え元のresolutionId、起動タイミング、発動条件をサーバーで再確認します。
対象は待機状態、または未開始・完了済みでgateがidleの効果だけです。コスト選択・支払い待ち・解決途中は拒否します。
新しい実行器を別に構築してコスト選択の開始まで検証し、成功時だけ差し替えます。
失敗しても元の効果と盤面は保持します。効果切替だけでカードやDONは移動しません。
移動ルールと数値評価方針は、待機セッションまたは直前の実行器を作成した信頼するサーバー設定を引き継ぎます。

同じrequestId・内容の再送は、プレイヤー別の記録から現在のviewを返し、再発動しません。
内容変更は拒否します。記録はテスト手番交代と共用で各プレイヤー1024件までで、上限後は新規要求を拒否します。
発動要求の記録は解決単位ではなく対戦所有者に保持し、次の効果へ進んでも消しません。
通常の効果操作とは別の記録領域です。成功時は既存の通信経路で両者に各自のviewを配信します。
回数制限など実カード固有のルール全般を保証する実装ではなく、実カード能力はまだ登録していません。

## 効果のない待機状態

サーバーがadopt後に `prepareRegisteredIdle(rules, numericPolicy?)` を明示的に呼ぶと、
実行器を作らずに盤面・進行状態・公開範囲別のviewを保持できます。起動時の空効果は不要です。
この設定にはカタログと発動許可が必要で、通常の所有者の動作は変更しません。

通信上の `effect.status: "idle"` は実行中の効果がないことを表します。
この間の `resolutionId` はサーバーが予約した「次の解決」のIDです。
snapshotのactiveResolutionIdはnull、selectionはnull、completedStepsは0です。
actorは待機中の手番プレイヤーを表し、手札等の公開範囲は既存の投影に従います。
一覧からの発動が成功したときだけ、この予約IDで実行器とコスト選択を開始します。
待機中に通常のstart/advance等を送っても処理は開始しません。

OwnedEffectEndpoint経由の処理完了後、および成功した支払い前のcancelCosts後は、
実行器を解放し、結果の盤面を保持して待機へ戻ります。次の予約IDは更新します。
支払い済み・解決中・失敗で停止した効果は自動解放しません。
終了した解決への通常コマンドは拒否し、発動要求の再送記録は保持して再発動を防ぎます。
待機からの参照・同期・次の発動も同じSocket所属チェックを通ります。

## ローカル専用の手番チェックポイント

`prepareRegisteredIdle(rules, numericPolicy?, true)` の第3引数で明示的に許可した、
非production・rulesがcertifiedNoneのテスト所有者に限り、待機中の手番側へ `testTurnSwitchAvailable: true` を返します。
通常の所有者では未許可です。処理中はこの許可を返しません。

クライアント要求は `test-effect:command` の `kind: "testNextTurn"` と、
matchId・予約resolutionId・requestId・両revisionだけです。移行先の手番やフェーズは指定させません。
所属・手番・メインの完了チェックポイント・待機・未終了・両revisionと予約IDを確認します。
発動要求と同じ対戦単位の再送記録を使い、連打や後から届いた再送で二重に進みません。

localTurnCheckpointは固定テスト専用です。既存Progressionの遷移で次の手番のmainを作り、
新しい手番側の付与DON回収・アクティブ化・通常ドロー・DON追加を1つの盤面トランザクションへまとめ、
盤面側のターン番号も更新してから、両状態を一括で保持します。
初回はサーバー内部のinitializeLocalTurnStartで、先攻にDON1枚だけを追加します。二重の初期適用は拒否します。
以後の通常ドローは1枚、DON追加は残り枚数を上限に2枚です。
数値修正・付与効果・公開中の一時スコープなど、未対応の状態が残る場合は開始を拒否します。
最後の1枚の通常ドローはドローフェイズで終了判定し、DON追加へ進みません。
失敗時は元の両状態を保持します。成功時は予約IDも更新し、両者へ各自のviewを配信します。
ターン開始/終了時の効果や期限解除を含む、正式なターン進行全体にはまだ対応していません。

## ローカルの山札切れ判定

ローカル手番交代を明示許可した所有者のみ、通常ドローおよびコマンド処理後の盤面で
山札0枚を検出し、既存ProgressionのfinishGameへ接続します。
片方だけなら相手を勝者に、両方なら勝者null・両者敗北にします。
この基準は[公式総合ルール](https://onepiece-cardgame.com/pdf/rule_comprehensive.pdf?20260109=)の敗北条件・敗北判定処理を参照しています。

effectの選択待ちや解決中でも終了が優先し、現在の実盤面を保持して実行器を解放します。
通常のキャンセルや巻き戻しではありません。支払い済みカードを手札へ返しません。
終了後も所有者とルームは保持し、再同期は可能ですが、発動・手番交代は拒否します。
過去の発動要求の再送は現在の終了viewを返し、効果を再実行しません。
公開viewのfinished/winnerに加え、山札切れの場合のみdefeatedPlayersを返します。
内部の終了理由文字列や非公開カード情報は返しません。
通常のオンライン対戦や、ローカル専用機能を許可しない所有者には追加していません。

## ローカル専用のテスト登場

ローカル手番交代を明示許可した所有者の待機中メインに限り、手番側へtestPlayAvailableを返します。
要求はtest-effect:commandのkindがtestPlayCard、matchId・予約resolutionId・requestId・両revision・source参照だけです。
actor、cardId、種類、移動先、枠番号、コストなどをクライアントから指定することはできません。
公開viewと同じフラグだけで許可せず、所有者がメインの権限・未終了・処理待ちなし・現在の予約ID・両revisionを再確認します。
実カード参照のgeneration・所有者・コントローラー・手札所属・表向きも確認します。

localCardPlayはカード種類から移動先を決め、キャラクターは最初の空き枠、ステージは空き枠だけを使います。
既存のMovementStoreで1回のルール移動を確定し、generation・characterのenteredTurnを既存ルールで更新します。
移動後は予約IDを更新し、相手へは登場カードを公開した各自のviewを既存Socket経路で配信します。
満杯・対象外カード・古い参照などの拒否時は盤面を変更しません。
再送記録は登録発動・テスト手番交代と共用し、同じ要求の再送で二重登場しません。

これは無料の配置テストであり、正式なカードプレイ処理ではありません。
実カードのcost/色条件や登場時の誘発処理は未接続で、DONを減らしたりレストにしたりしません。
productionや明示許可のない所有者では拒否します。通常オンライン対戦・一人回しのプレイ処理は変更しません。

## ローカル専用の攻撃宣言と防御側の判断

ローカル機能を許可した所有者にのみ、testAttackAvailableと、公開盤面上の
testAttackSourceIds/testAttackTargetIdsを返します。候補は表示用で、実行時の検証を省略しません。
待機中のメイン・未終了・手番・各自の初回ターン・カードの所属/種類/状態/enteredTurnを確認します。
攻撃元は自分のアクティブのリーダー/キャラ（登場したターンを除く）、攻撃先は相手リーダー/レスト中の相手キャラです。
修正値や付与効果など未対応の状態がある場合は、通常の攻撃可能性を勝手に推測せず拒否します。

test-effect:commandのtestAttackは、通常のmatchId・予約resolutionId・requestId・両revisionと、
source/target参照だけを受け付けます。サーバーがbattleIdを生成し、攻撃元のsetRest(true)と
ProgressionのstartBattleを一括保持します。固定テストではアタック時効果を実行せず、block判断待ちへ進みます。
公開viewのbattleは公開済みの盤面カード参照と判断状態のみで、手札・マスター定義は含みません。
通常viewだけでなく、カウンター効果処理中のviewにもbattleを保持し、表示用の矢印を維持します。

testBattleDecisionは通常のコンテキストとbattleId、decision（passBlock/endCounter）を受け取ります。
testBattleDecisionフラグを渡すのは現在判断する防御側だけです。サーバーで役割・段階・待機・未回答を再検証します。
ブロックを行わない判断→counter、カウンター終了→damageの順に進みます。判断操作ではカードを移動しません。
効果の解決中・選択待ちには判断終了できません。過去の判断の再送で次の段階を飛ばすこともできません。
要求記録は他のローカル操作と共用し、各自1024件を上限にします。

damageでは防御側の明示的なtestResolveDamageを待ちます。判断が終わっただけでは自動でダメージを適用しません。
途中で参加カードの位置やgenerationが変わった場合も、別カードへ勝手に矢印を付け替えず拒否します。
ブロッカー能力判定・速攻等の個別能力・誘発処理は次段階です。正式なカード効果全般の合法性は保証しません。
通常オンライン・一人回し・手動テスト対戦のアタック処理は変更していません。

### ローカルのテストブロック

明示的にローカル操作を許可したownerだけがtestBlockを受け付けます。本番環境・既定ownerでは使用できません。
testBlockCandidateIdsは防御側のblock判断中だけ、自分の表向きアクティブキャラを公開参照IDとして返します。
マスターにブロッカー能力情報がないため、能力や禁止条件の合法性判定ではなく進行用フィクスチャです。
要求はmatchId・予約resolutionId・requestId・両revision・battleId・blockerのinstanceId/generationだけです。
候補と両参加カードを再検証し、絶対指定のsetRest(true)とredirectBattle→block完了→counterを候補状態として構築後、一括保持します。
攻撃元は一切変更せず、以後の矢印・パワー比較・KOは新しい攻撃先を使用します。
効果処理中・ライフ選択中・別プレイヤー・レスト済み・古い参照・余分な権限フィールドを拒否します。
要求記録は既存の共通レシートを使用し、同一要求の再送で再レスト/再リダイレクトせず、変更された再送はrequest_conflictです。

### ローカルの手札カウンター

testHandCounterは防御側のcounter判断窓だけで、指定された自分の手札キャラを1枚トラッシュへ移します。
要求は既存の共通コンテキスト・battleId・card(instanceId/generation)だけです。数値や移動先のクライアント指定は拒否します。
値は固定済みマスターのcounterを再検証します。正の安全な整数で、種類がcharacterまたはunknownの場合だけ使用します。
候補testCounterCandidatesは防御側にのみ送信し、相手には空配列を送信します。使用後は通常の公開トラッシュとして見えます。
移動と加算値を候補として構築し、検証成功後にownerへ一括保持します。失敗した要求ではどちらも変更しません。
加算値はowner内のbattleId別コンテキストに保持し、battleCounterとして双方へ投影します。
同じバトル内の効果解決をまたいでも保持し、終了/新規バトルでは持ち越しません。カード自体の永続パワーは変更しません。
加算・基礎パワーとの合算が安全な整数に収まるかを検査し、不明の基礎値は0にしません。
既存レシートと両revisionで、再送/古い参照/別プレイヤー/選択窓終了後の二重使用を防止します。
これはローカル検証用のキャラの数値カウンターだけです。イベント効果やカード固有のカウンター制限は処理しません。

## ローカル基本ダメージとパワー情報

loadMasterで検証・freezeしたマスターを、対戦開始前のpinLocalBattleMasterで1回だけ固定します。
効果DSL用のlegacy.masterは引き続きnullのままとし、従来の種類不一致による開始失敗の経路を復活させません。
使うのは公開されているバトル参加カードのpowerのみです。マスター全体や手札の数値をクライアントへ送りません。
公開viewのbattlePowerにはattack/defense（不明ならnull）とmasterVersionだけを含めます。
明確な種類矛盾、欠損、未対応の修正値、オーバーフローはunknownとして停止します。0は有効な既知値です。
攻撃側は基礎パワーと付与DON×1000、防御側は基礎パワーと確定した手札カウンターを使います。防御側の付与DONは加算しません。個別能力は未接続です。

testResolveDamageはmatchId・予約resolutionId・requestId・両revision・battleIdだけを受け付けます。
防御側のdamage段階、解決待ちなし、未終了、両参加カードの現在の位置/generation、既知の数値を再確認します。
クライアントからパワー、勝者、移動カード、移動先を指定することはできません。
攻撃側が防御側以上ならBATTLE_KOまたは1ダメージを既存MovementStoreへ渡します。
KOに伴う付与DON戻しは既存の自動処理を使用します。
リーダーへの基本ダメージはライフ一番上をdefender限定のrevealスコープで確認し、choiceゲートで待ちます。
実カードのfaceUpは変更せず、相手へ新しいカードIDやrefを送りません。選択tokenはdefenderにのみ渡します。
testDamageChoiceは予約resolutionId・両revision・battleId・selectionId・不透明tokenを検証し、移動先はサーバーが決めます。
手札選択は非公開手札へ、トリガー選択は表向き公開エリアへ移動し、revealスコープを同一Movementトランザクションで閉じます。
位置/generation/最上段も再確認し、古い選択・別プレイヤー・変更された再送を拒否します。同一要求再送では二重移動しません。
選択中は進行ゲートとownerのpending状態で他の操作・効果開始を拒否します。再同期でも同じ選択を維持します。
トリガー所持・固有効果の実行は未接続で、すべての確認カードで宣言/公開だけ選択できるローカル限定の動作です。
