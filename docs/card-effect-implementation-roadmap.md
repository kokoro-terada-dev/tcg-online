# 隔離v3 効果拡張ロードマップ

基準: `0cd0883` / 2026-10-29。これは実装計画であり、以下はまだ実装していません。
元の段階1〜6の限定対戦を置き換える計画ではなく、その外側に残った機能を小さく追加します。
通常対戦・一人回しは対象外です。DB復旧/本番移行もこの効果拡張とは別の計画にします。

## 1. 推奨順序

最初にデータの保留と読み取りモデルを固め、簡単なメタデータ検索を増やします。
その後にMAINの発生元/イベント、条件付き誘発、効果登場、DON、手札操作を接続します。
継続・耐性・置換は影響が広いため、共通の原因/実効値/中断機構ができてから分離して実装します。
「件数が多い機能」だけを先に選ぶと、誤った成立条件や支払いモデルを前提として作り直すことになるためです。

```text
PR00 出典と差異保留
  -> PR01 文脈/実効値の読取契約
     -> PR02 メタデータ -> PR03 集合条件
     -> PR04 MAIN発生元 -> PR05 単純イベントMAIN
     -> PR06 条件付き誘発 -> PR07 追加timing/期限
     -> PR08 移動結果/効果登場 -> PR09 DON効果操作
     -> PR10 cost/モード/途中支払い -> PR11 非公開手札
     -> PR12 継続効果 -> PR13 耐性/防止 -> PR14 選択待ち置換
     -> PR15 本文呼出 -> PR16 追加バトル機能
各段階の承認レビュー -> PR17 カタログ分割・追加カードの反復
```

これは主経路です。各PRの必要依存は次節に記載します。例えばPR08にはPR02/03/06、PR14にはPR10/12/13が必要です。
番号は日付でも工数見積もりでもありません。複雑ならa/bへ分割し、後続機能まで一度に受理しません。

## 3. 各PR共通の完了条件

1. 原文・参照版・公式根拠・未確定項目を代表カード単位で記録する。
2. 新ノードの型/Schema/Compiler/Runtime/work/投影/画面が必要範囲でそろう。受理するだけのschemaOnlyは出さない。
3. 不明値、未知ノード、非法参照、未対応の場面は拒否する。
4. Compiler負例・Runtime境界・代表カードの期待結果・選択中断/再開・両操作者を確認する。
5. 非公開情報、actor/revision/token、再送/重複支払い/古い世代を確認する。
6. フロント/サーバーのbuildが通る。既存限定プリセットと通常/一人回しの変更対象を確認する。
7. ガイド/命令一覧/実装状況を実際の対応範囲へ更新し、独立承認が必要なら対象ごとに確認する。

普段はビルドと該当差分の軽量テストに留めます。
ただし非公開手札・支払い・置換・継続の共通基盤を変更するPRでは、影響する既存の秘匿/原子性/期限テストを省略しません。
UIの実機操作確認は利用者が行い、未実施を成功と報告しません。

## 4. 互換性と承認版

各機能を追加する際にschemaVersion/Compiler/handler/frame/rulesetのどの版が変わるかを明示します。
署名した古いframeを新プログラムとして黙って再開しません。移行不能なら既存試合は旧版のまま、または安全に終了します。
registryHashが変わった場合、既存のtrusted approvalはそのまま新カタログへ通りません。
ハッシュを一括上書きして「再承認済み」にするコマンドは作りません。
旧カタログを固定して併存させるか、対象定義と根拠を個別確認して新しい署名/承認を配置する手順を選びます。

回帰時には通常対戦のBoard/store/roomと一人回しを修正しない原則を守り、隔離v3の入口だけを切り戻せるようにします。
未完了PRのノードはRegistryへ登録せず、画面からも選べない状態にします。

## 5. カード単位の受け入れ

カードには次の追跡状態を提案します。既存reviewStatusを変更する提案ではなく、外部レビュー台帳の状態です。

```text
raw_source
 -> data_hold / variant_hold / needs_review
 -> clauses_mapped（全本文・トリガー・キーワード）
 -> compiler_verified
 -> runtime_scenarios_verified
 -> ruling_verified
 -> individual_approval
```

どこか1つの能力を未対応のまま省略するとclauses_mappedを満たしません。
候補の大量生成は最初から2,885枚を対象にせず、機能がそろった20〜30枚程度で往復検証します。
代表テストが通ったことを同じタグ全件への承認に拡大しません。

## 6. 実装開始時の最初の依頼案

まずPR00/01の範囲に限定し、原資料・保留版を保持するレビュー台帳と、既存の読取結果を変えないEventContext/DerivedFacts契約を固めます。
その後、OP01-016を代表として名前除外・特徴一致のCompiler/Runtime/選択UIテストを追加します。
継続/置換/効果登場を同じPRでまとめて実装しないことを推奨します。
この資料作成の承認は、ここに記載したゲーム処理変更をすでに許可したという意味ではありません。
