# Cost：複数コストのリソース計画と再検証

後続の [Action実行器](action-runtime.md) では、payDonだけの定義に限りCostPlanSessionの計画をMovementResolutionへ接続し、DONの一括レストまで実行します。本書のCostPlanSession自体は引き続き計画と再検証だけを行い、複合コストや既存対戦の支払いには未接続です。

## 今回の範囲

支払い前のスナップショットから、複数コストをまとめて満たすカード/DONの組み合わせを検証します。
実際のカード移動、レスト、公開、発動の確定は行いません。
既存対戦・UI・Socket.IO・カードマスターは変更しません。schemaOnlyの効果定義を、全機能実行可能には変更しません。

| ファイル | 役割 |
| --- | --- |
| `effects/costTypes.ts` | コスト用スナップショット、選択、要求、操作計画の型 |
| `effects/costs.ts` | 型付きCost実行Registryと共通の支払い要件 |
| `effects/costPlan.ts` | 複数グループの割当検証・重複防止・確定前の再検証 |
| `test/costs.cjs` | 複合コスト、割当、失敗時の非変更、権限、世代・状態のテスト |

## 独立した支払いと、順序に依存する支払い

呼び出し側はsemanticsを必ず明示します。値を省略して推測させることはできません。

- `independent`：それぞれを支払い前の同じ状態で確認でき、同じ実体を複数のコストで使用しない方式。
- `ordered`：順番により状態や条件が変わる方式。現在はunsupportedを返し、実行しない。

例えば同じDONをレストしてから戻す、同じ手札を公開してから捨てる、前段で戻ったカードを後段の支払いに使う場合は、単純な重複禁止だけで裁定しません。
そのようなカードをindependentに分類してはいけません。カードテキストと裁定に基づく分類・順序付きの仮実行は、後続フェーズで設計します。
本モジュールがカード文を読んでこの分類を自動決定することはありません。クライアントに自由指定させる項目でもありません。

## 現在の支払い要件

| kind | 計画する内容 |
| --- | --- |
| payDon | 自分所有・自分管理のACTIVE DONを指定枚数選び、レストの操作を計画 |
| restCards | 自分のリーダー・キャラクター・ステージ・ACTIVE DONからアクティブな対象を選択 |
| moveCards | 自分の手札・キャラクター・ステージのトラッシュ、自分のキャラクター・ステージの手札戻し、ACTIVE/REST DONのDONデッキ戻し |
| revealCards | 条件に合う自分の手札の公開操作。カードを公開エリアへ移動する処理ではない |

DON-1/-3、アクティブDONのみの戻しはmoveCardsの枚数・選択元で表現できます。
SOURCE以外、特徴を持つ手札などの条件は既存のSelector/Predicateを使います。
revealCardsの構造検証をDSLへ追加しました。既存のDSLにこの命令を強制追加する変更ではありません。

この段階では選択者・所有者・コントローラーを支払う本人に限定します。別プレイヤーによる選択、RANDOM/BLIND_SELECTでのコストは未対応です。
付与されたDONは独立した所在・参照モデルが未実装のため扱いません。コスト用スナップショットでactiveDonなどへ偽装してはいけません。
DON付与、付与DON戻し、特殊な支払い軽減・置換・免除も後続対応です。
これらの制限は現段階の実装範囲であって、カードゲームの合法/非合法の裁定ではありません。

## 情報源

CostSnapshotは既存のSelectionSnapshotに、サーバーが管理するkindとrotatedを加えた内部モデルです。
kind/rotatedとFactsの重複項目が矛盾しても、候補判定にはサーバーの実体側を使います。
ハンドラーへ渡すスナップショットは元データから切り離してfreezeし、元のカードや配列を変更・freezeしません。
枚数やマスターが足りないことを0や支払い済みと解釈しません。必要な種類・条件が不明ならunknownとして止めます。
カードIDや画像からカードの能力・種類を推測しません。
現在のMatchからこのモデルを組み立てる接続コードはまだありません。

## 計画の流れ

1. 型・構造検証済みのcostsと、同一revisionのサーバースナップショットを用意する。
2. CostRegistryで要件を作り、Selectorで各グループの候補を生成する。
3. 既に選ばれた実体と枚数・世代・操作可能性を検証する。
4. 選択済みカードの重複を確認し、未選択グループには残りの実体を割り当てられるか検証する。
5. 選択が未完了ならselectionRequired、全選択済みならresourcePlanを返す。

割当には二部グラフのマッチングを使います。最初のグループへ貴重なDONを機械的に割り当て、別の合法な組み合わせを見落とす貪欲処理にはしません。
既に固定した選択により残りが支払えなくなった場合も、盤面を変えずunavailableを返します。
pendingな要求のSelectorには、他の固定コストで使用済みの実体と、その操作で使用できない実体の除外条件を加えます。
選択要求はサーバー内部用です。既存のSelectionSessionでトークン化してから表示する必要があります。
個別には候補でも、複数枚をまとめて選んだ組み合わせが残りの支払いを妨げる場合があります。回答ごとに全体を再計画しなければなりません。

## 結果と原子性の境界

戻り値はplanned / selectionRequired / unknown / unavailable / unsupportedです。
plannedの中身はstatus=resourcePlanであり、支払い済みreceiptではありません。
計画にはCOST_PAYMENTを原因とする移動、レスト、公開の操作記述と、使用する実体・saveAsの内部結果だけを保持します。
saveAsの参照は現段階では支払い前の世代です。実際の移動後に同じ参照が有効だと扱わず、共通移動器の結果から前後の世代・参照可能な結果を対応付ける必要があります。
revealはカードを手札に残したまま公開する予定です。実際の公開Viewや公開期間はまだ実装しません。
計画成功・途中失敗のどちらでも元のカードや盤面は変更しません。

CostPlanSessionは元の要求と選択をコピーし、validateForCommitで最新状態から同じ計画が成立するか再検証します。
対戦ID・revision、世代・所有者・管理者・所在・表裏・種類・レスト状態・現在の選択条件を再確認します。
Session自体はJSON.stringifyを拒否します。resourcePlanやsaveAsの実体参照も内部情報であり、そのまま公開しません。

**validateForCommitを呼んでも支払いは行われません。同じスナップショットから複数の計画を作ること自体は可能です。**
別計画間の二重支払い、通信の再送による再確定を防ぐには、今後の共通移動器で次を同一トランザクションにする必要があります。

- 最新revisionと計画の再検証。
- 支払い全体の盤面変更。
- 発動確定・選択結果の保持・進行gateの更新。
- revision更新と要求IDの完了記録。

一部をレストにした後で手札破棄を失敗させるような実装には接続しません。
対象キャラクターが場を離れる際の付与DON返却、場を離れない効果、コストへの置換などは共通移動・ルール層で解決する必要があります。
そのためresourcePlanだけを根拠に「発動可能」「支払い完了」と表示してはいけません。

## 拡張と制限

CostMap、構造パーサー、CostRuntimeRegistryのハンドラーを登録します。未知命令は無視しません。
現在の拡張も標準のrest/move/reveal操作へ変換し、共通の所有権・重複・実体検証を通す方式です。
最大16コスト、1グループ128候補、全体128実体、マッチング作業32,768単位を上限とします。上限を超えた結果を、通常のコスト不足として決めつけません。
SELECT/ORDERには本人の明示的な選択が必要です。ALLだけは全候補を固定します。空コストや明示的な0枚選択も扱えます。
選択済み実体の並びを支払いのルール順序と同一視しません。独立コストの操作記述は定義順に並べます。
